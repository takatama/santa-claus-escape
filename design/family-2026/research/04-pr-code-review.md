## 0. 結論

**推奨：PR #1 はマージせずに保持し、必要な部分だけを新しいアプリへ移植する（後述の案C）。**

価値があるのは次の3つで、ページ構成そのものではない。

## 5. 状態管理の正しさ（`journey/state.js`・`journey/store.js`）

### 5.1 設計の要点【確認済】

- **単一の保存レコード** `{ generation, state }`（`store.js:57-71`）。保存するたびに最新を読み直し、`update(state)` を適用して丸ごと書き戻す。そのため、別ページが同じ世代で行った保存は失われない
- **世代による古いタブの拒否**：`reset()` が新しい UUID 世代を書き込む（`store.js:73-81`）。各ページは `read()` で読んだ世代と保存時の世代を比べ、違えば書き込まない（`store.js:61`）
- **会話の多重クリック防止**：`expected: { phase, revision, questionId, reinvited }` が一致しないイベントは捨てる（`state.js:176-182`）。受付票（receipt）で「自分のクリックが受理されたか」を区別する（`store.js:92-96`）
- **不変条件**：次の状態は作れない
  - 解錠していないのに紙を持っている
  - 紙を持っていないのに枠へ置いている
  - 合言葉を唱えていないのに発見している
  - 発見していないのに会話が進んでいる

  紙を一度取得したら、ふたを閉じても失わない（`state.js:41-50, 107-111, 133-151`）
- **移行**：v1 の旧レコード（`generation` の包みがない形、`discovery` / `conversation` / `introduction` がない形）は `Object.hasOwn` で既定値を補って読む（`state.js:99-116`、`store.js:17-19`）

**評価**：小さなステートマシンを厳密に守る姿勢は良い。特に「受理していない入力は元の参照を返す」規約は、純関数として扱いやすい。

### 5.2 問題点

**(1) 検証が全か無かで、読めない保存を黙って上書きする — CONFIRMED（製品では重大）**

- `restoreJourney` は、どこか1か所でも条件を満たさないと全体を `null` にする（`state.js:94-116`）
- `parseRecord` は `null` を受けると `newJourney()` を返す（`store.js:10-22`）
- 次の `save()` はその空の状態に更新を適用して `setItem` する（`store.js:60-68`）。退避も警告もない

再現（scratchpad の probe1.mjs）：

```
read() of v2 record -> papers: []
after one save: generation= initial  version= 1  red= {"unlocked":false,"progress":0,...}
valid journey papers: 2  restore with 65-char draft -> null
```

- `version: 2` のレコード（赤箱は解錠・取得済み）を置き、青箱を1回保存しただけで、赤箱の進行が消えた
- 下書きが65文字の journey は、紙2枚を持っていても丸ごと `null` になった

影響【推定】：

- バージョンが混在すると消える。デプロイ後も古いタブが開いたまま新版のレコードを読めば、古いコードがそれを初期状態で上書きする
- 内容の微調整でも消える。例えば `witch/conversation.js:37` などの別名（aliases）に答えを追加すると、`conversation.js:68` の `response.correct !== matches(...)` で過去の回答記録が不正扱いになり、保存全体が消える
- 閾値の変更でも消える。紙の授与閾値を変えると、`validBox` の「到達したのに未取得」判定（`state.js:48`）に引っかかる

対策：

- 区画ごとに検証し、壊れた区画だけを既定値に戻す
- 読めないレコードは別キーへ退避する
- 前方互換のためにバージョンで分岐する
- 内容に依存する値（正誤）は保存せず、読み込み時に導出する

**(2) 紙の授与閾値が箱ごとに違う — CONFIRMED（UX の不一致）**

| 箱 | 授与の条件 | 取っ手の矢印の切り替え |
|---|---|---|
| 赤 | `p >= 0.98`（`red-box/box-math.js:53`） | `> .98`（`red-box/main.js:327`） |
| 青 | `p === 1`（`blue-box/box-math.js:54`） | `>= 1`（`blue-box/main.js:295`） |
| 黄 | `p === 1`（`yellow-box/box-math.js:56`） | `>= 1` |

- probe の結果：開き 0.99 で、赤は `awarded: true`、青は `false`
- 青・黄では 99% まで開けても「二枚の紙が見えてきた。もう少し…」のままになる
- テスト（`journey/test.mjs:59-81`）は 0.97 / 0.98 / 0.999999 / 1 という**この不一致そのものを仕様として固定**している

**(3) 保存が使えない環境では、合言葉の先へ進めない — CONFIRMED（起こる頻度は SUSPECTED）**

- `letters/main.js:255-258`：保存が使えないと「…次の場面へ進めません」と表示して止まる。発見へのリンクも隠す（`letters/main.js:118`）
- `witch/main.js:21, 56`：救出への移動とリンクも止まる
- ページ間の受け渡しが localStorage しかない MPA 構成なので、こうなるのは構造上避けられない

【推定】iOS Safari の「すべての Cookie をブロック」や保護者制限のある端末では、`localStorage` へのアクセスが例外になる。その環境では最後まで遊べない。

**(4) タブ間調停が複雑すぎる — 設計上の指摘**

- `journey/test.mjs` の31件のうち13件（42%）が、別タブ・古いクリック・世代・受付票の検証に使われている
- 世代と受付票に関わるコードは25か所ある

【推定】子どもと親が1台で遊ぶアプリでは、1タブで完結するアプリ（SPA）にするほうが割に合う。他のタブで開かれたら BroadcastChannel で「別の画面で開いています」と知らせれば十分。

**(5) その他【確認済】**

- `version: 1` を直接書いている（`state.js:19, 95`）。移行関数の仕組みがない
- `restoreJourney` を1回の更新で2〜3回呼び、`JSON.stringify` で比較している（`state.js:81, 111`）。規模が小さいので性能上の問題はない
- `navigation.js:7` は呼ぶたびに `createJourneyStore()` で新しいストアを作る。害はないが、責務がはっきりしない

## 9. アクセシビリティ（マークアップ）

### 9.1 良い点【確認済】

- `lang="ja"`。ボタンとリンクはネイティブ要素
- 拡大調査は `<dialog>` を `showModal()` で開く。Esc（`cancel`）と外側クリックで閉じ、開いたときに錠の現在桁へフォーカスを移す（`red-box/inspection.js:306-312`）
- 四桁錠の各桁は `role="spinbutton"` と `aria-valuenow` を持つ。↑↓・←→・数字キーで操作でき、上下ボタンは `tabIndex=-1`（`red-box/cylinder-lock.js:130-161`）
- ドラッグには必ず代わりの操作がある。枝とふたにはスライダーと「少し開ける」ボタン、紙の並べ替えには「選択→枠をタップ」・矢印キー・Delete キーがある（`letters/main.js:146-187, 237-245`）。WCAG 2.5.7 の考え方に沿っている
- `aria-live="polite"` のナレーションは、しきい値を越えたときだけ更新する（`lastNarration`）。場面が変わると見出しへフォーカスを移す（`witch/main.js:157`、`intro/main.js:66`）
- `prefers-reduced-motion` は JS（`red-box/main.js:400`、`main.js:310`）と CSS の両方で尊重している。`:focus-visible` も定義している

### 9.2 課題

- **文字が小さい**【確認済】：モバイル時の副題は9px、リセットボタンは10px、操作ボタンは11px、スライダーのラベルは10px（`style.css:158, 209-218`）。大人と子どもで画面を覗き込んで使うには小さい

  - `index.html:15` は `role="img"` なのに `tabindex="0"` とキー操作を持つ
  - `red-box/index.html:18` は role を持たずにフォーカスを受ける
- **`explore/index.html:40` のナレーションに `aria-live` がない**【確認済】
- **子どもの読み書きへの配慮がない**【確認済】：ルビ（`<ruby>`）が一つもない。音声もない（`AudioContext`・`<audio>`・`speechSynthesis` の使用がない）

### 10.2 課題

- **実機テストがない**【確認済】：390×844 のビューポートをエミュレートしただけ（`qa/PR-VERIFICATION.md`）
- **古い iOS では動かない — SUSPECTED（実機未確認）**
  - `ctx.roundRect` が無条件で17か所（`red-box/main.js` など）。Safari 16 以降の機能なので、iOS 15 止まりの端末（iPhone 6s / 7 / 初代 SE、iPad Air 2、iPad mini 4）では描画中に TypeError になる
  - `Object.hasOwn`（`state.js:101-114`、Safari 15.4 以降）、`dialog.showModal`（15.4 以降）、`inert`（15.5 以降）も同じ系統
  - 【推定】家庭で子どもに渡すお下がり端末にはこの層が含まれる
- **縦長・横長の判定が場面ごとに違う** — CONFIRMED（影響は小さい）

  | 場面 | 縦長の判定 |

### 11.3 描画の負荷

- **CPU で余白を切り取っている**【確認済】：`rescue/paint.js:1-20`（と `main.js:37-62` の写し）は、読み込みのたびに `getImageData` で全画素を JS のループで走査し、透明な余白を切り取る。森のページでは約1,250万画素を走査する。【推定】ビルド時に一度だけ行えば不要になる
- **メモリ**【推定】：森のページで画像を展開すると RGBA で約57MB。余白を切り取る間は一時的に約100MB（作業用 canvas と `getImageData`）、切り取った複製で約50MB が加わる。iOS Safari の canvas メモリ上限に注意が要る
- **毎フレーム約1,100回の画像描画**【確認済】：箱の場面では1回の `render()` で次の三角形を描く。各三角形は、クリップしたうえで画像全体を `drawImage` する（`rescue/paint.js:30-61`）

  | 対象 | 三角形の数 |
  |---|---:|
  | 枝（9×12×2×左右） | 432 |
  | ふた（12×7×2） | 168 |
  | ふたの雪（12×7×2） | 168 |
  | 球（12×14×2） | 336 |
  | 合計 | 約1,100 |

  - 箱の場面では枝は固定（`amount` は 0 または 0.055）なのに、毎フレーム描き直している
  - ポインタが動くたびに、rAF でまとめずに同期で `render()` している（`red-box/main.js:456-460`）
- **デスクトップでの計測**【確認済】：発見の場面（DPR 2、1024×616）で、毎フレーム `render()` を走らせた120フレームのフレーム間隔は、中央値16.7ms・90パーセンタイル16.7ms・最大17.7ms。60fps を保っていた。JS 側の同期処理は中央値1.7ms
- **モバイルは未計測** — SUSPECTED：中位〜低位の Android と古い iPad では、ドラッグがカクつく可能性がある
- **無限ループはない**【確認済】：常時回る rAF ループはなく、アニメーションはすべて期限つき（440ms の補間、雪の演出1.15〜1.9秒など）。描画は変化があったときだけ行う
- **観測メモ**：計測用ブラウザのペインが非表示（`visibilityState: hidden`）の間は、`img.decode()` が5秒以上解決しなかった。画像は読み込み済み（`complete: true`）だった。森のページは「読み込んでいます…」のまま止まっていた。【推定】ページが表示されれば解決するので、通常の利用では問題になりにくい。ただし、読み込みをすべて `decode()` 待ちにしているため、表示されるまで何も描かれない

### 15.2 書き直すもの

1. **アプリの骨格**：9つの MPA と `?journey=1` の二重モードをやめ、1つのページに場面を切り替えるルーターを置く構成にする。これで次が手に入る
   - 場面間のトランジション（ページをめくる、光でつなぐ）
   - 次の場面の画像の先読み
   - 保存が使えなくても、メモリ上で最後まで遊べること（B5 の解消）
   - タブ間調停（世代と受付票）の大部分が不要になること
2. **保存**：次の5点を備えた保存層にする（B1 の解消）。
   - スキーマのバージョンと移行関数
   - 区画ごとに寛容な復元
   - 読めないレコードの退避
   - 導出できる値（正誤など）は保存しない
   - BroadcastChannel で「別の画面で開いています」と知らせる
3. **箱の場面**：赤・青・黄の写しを1つの BoxScene と3つの設定にまとめる。閾値、ナレーション、手がかりの絵、誤答ヒント（赤・青にも入れるかを含めて）を設定で揃える（B2 の解消）
4. **描画のパイプライン**
   - rAF で入力をまとめて描く
   - 背景と枝を層ごとにキャッシュし、動く層だけ描き直す
   - レスポンシブな画像セットを用意する
   - テスト用の `dataset` は本番では書き込まない（B8 の解消）
5. **品質保証**
   - Playwright の E2E を CI に入れる。入口→三箱→紙→発見→会話→救出の通しと、390幅・タッチ・iOS Safari のエミュレーション
   - QA の画像は CI の成果物として出し、リポジトリにはコミットしない
6. **文字と読みやすさ**：本文と操作の文字を14〜16px以上にする。ルビの表示切り替えと、読み上げ（main の `prototype/` にある Gemini TTS の台詞 WAV 93ファイルを流用できるか検討する）を加える。リセットには確認を入れる（B3 の解消）
7. **互換性の方針**：対応 OS の下限を決める。iOS 15 を切るか、`roundRect` などに代替実装を用意する（B10）

### 15.4 PR #1 の扱い：3案の比較

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| **A：アーカイブ試作として現状のままマージ** | そのまま main へ入れる | 作業が main に残る。手間がゼロ | main から辿れる履歴が +64.5MB（+78%）。QA 画像178枚、未使用10.8MB、個人パス15ファイル、CI 未接続のテストが main に常駐する。「試作」と「製品」の区別がつきにくくなり、これを土台に継ぎ足したくなる |
| **B：直してからマージ** | QA 画像・未使用素材・個人パスを除き、PNG を WebP にし、`NOTICE.md` を更新し、CI に接続し、B1〜B4 を直してからスクワッシュマージする | main は軽く保てる（スクワッシュなら旧 PNG の blob は main に入らない。【推定】素材は約5MB 程度になる） | 置き換える予定の骨格（9ページと三箱の写し）に手を入れることになり、コストが返ってこない。直した後も二重モードと MPA の構造は残る |
| **C：マージせずに保持し、必要な部分を移植**（推奨） | PR はドラフトにするか、理由を書いてクローズする。参照用のブランチは残すか、別リポジトリへ退避する。§15.1 の対象を新しいアプリへ移植する | main を汚さない。良い部分（素材・仕掛け・数学・状態遷移）だけを、テストつきで新しい構成へ入れられる。クリスマスまでの約11週を骨格の作り直しに集中できる | 作業の成果が main の履歴には直接残らない（PR とブランチで参照する）。移植作業が要る |

**推奨は案C。**

1. **価値のある部分は全体のごく一部**：生成画像と、合計1,000行足らずの純関数モジュール、触る仕掛けの設計。重さの大半を占める PNG（59%）と QA 画像（31%）は、そのまま持ち込むべきものではない
2. **骨格がそのまま負債になる**：§3（重複と二重モード）と §5（全か無かの保存、保存できない環境での行き止まり）は、局所的な修正では直らない
3. **品質の担保が移植先で作り直しになる**：UI の約85%が自動テストなしで、CI にも未接続。どちらにしても移植先でテストを作る必要がある
4. **基盤としての制約になる**：家族向けの製品として外せない「読み上げ・ルビ・大きな文字・古い端末・確認つきリセット」が、どれも現在の骨格にない

補足【推定】：

- リモートにブランチやタグが残っている限り、通常の `git clone` はそれらのオブジェクトも取得する。リポジトリを軽くしたいなら、試作は別リポジトリか Release の zip へ退避し、ブランチを削除する方法もある
- オーナーが「main で見られる状態にしたい」なら、案B を簡略化して `archive/illustrated-prototype/` にスクワッシュマージする手もある。その場合、QA 画像は除き、素材は WebP にし、二重モードはそのままにする
